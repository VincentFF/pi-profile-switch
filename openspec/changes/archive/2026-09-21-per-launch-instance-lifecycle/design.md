# Design

## Context

Motivation in `proposal.md`. Below are the current-state constraints that shape the design and are written nowhere else:

- `PI_CODING_AGENT_DIR` cannot change after the child process starts. In-session `/profile use` can only rewrite the current instance directory, so a fixed "directory name equals profile name" path inevitably stops matching its content after an in-session switch.
- The instance's symlink mirror is **a snapshot taken at generation time**: only entries already existing in the real agentDir get linked; entries created inside the instance at runtime exist only in that instance.
- pi-subagents' store is derived from `getAgentDir()` (`<agentDir>/missions/projects/<project-hash>/`); its ledger `missions/index/*.json` records **absolute** `recordPath`s, and when reading the ledger, a nonexistent path is dropped as stale. Record bodies are read by directory (`readMission` / `listMissions` go through `missionDir/<id>.json`).
- pi-profile's own runtime state lives in `~/.pi-profile-switch/pi-profile-state.json`, not inside the instance, and is unaffected by the instance lifecycle.
- The pid-liveness mechanism the sweep needs, and its grace period (covering the race between `mkdir` and the pid write, and crashes before the pid is written), already exist and can be reused as-is.

## Goals / Non-Goals

**Goals:**

- An instance's lifecycle equals one launch: concurrent launches of the same profile do not interfere, and in-session switching touches a directory owned by that session alone.
- Dead instance directories converge to reclamation, and reclamation does not destroy data not generated by pi-profile.
- Third-party state created at runtime lands in the real agentDir — no second copy inside the instance, and no instance paths written into third-party data.

**Non-Goals:**

- No migrating, absorbing, or rewriting of 0.4.x and 0.1–0.3 legacy directories or the absolute paths inside them.
- No automatic discovery of third-party extensions' state directories (discovery would require executing extension code, already excluded by existing design).
- No inner seed for third-party state inside managed directories (e.g. extension configuration under `extensions/`); those are named by the warning when they surface as unrecognized entries.
- No deletion at exit.

## Decisions

### 1. One unique instance directory per launch

Path shape `instances/launch-<random id>`; it is the agentDir handed to Pi. The random id is produced by the generation flow, and `pid` is written at the instance root.

Rejected design A: keep `instances/<profile>/agent`. Concurrent launches of the same profile would rewrite each other's managed files and `pid`; in-session switching would rewrite a directory another session is using; and the directory name would stop matching its content after a switch.
Rejected design B: path fixed per profile, content wholesale-replaced each time for consistency. The path is still shared per profile, and in-session switching's concurrency conflicts are unchanged.
Rejected design C: an always-stable path with nothing replaced. That is the status quo — giving up reclamation entirely.

ADR required: per-launch-instance-lifecycle

### 2. Reclamation happens only in the startup sweep; no deletion at exit

Every exit path (normal, signals, `SIGKILL`, power loss) terminates the child process, making `pid` a decidable fact, so the next launch's sweep always converges; the worst case is one leftover directory. Putting deletion on the exit path buys immediate tidiness at the cost of deletion logic on signal paths.

### 3. "Unrecognized entry" determination does not compare against the real agentDir

An entry is unrecognized when it is neither a symlink nor a managed artifact generated by pi-profile. Managed directories (e.g. `extensions/`) are also inspected, because third parties may write their own configuration inside managed directories. A hit keeps the directory and produces a warning instead of deletion.

The key point is **not** using "a same-named entry exists in the real agentDir" as a deletable condition: once the seed creates `missions` in the real agentDir, a same-named real directory inside a legacy directory would be judged "has a counterpart" by that condition and silently deleted — exactly the accident this rule exists to prevent.

### 4. Anchor runtime state in the real agentDir with seed symlinks

Before mirroring, seed the state paths Pi creates at runtime, then let the existing full-mirror logic produce the in-instance symlinks:

- Directories (`sessions`, `missions`) are created under the real agentDir when missing (an empty directory carries no content semantics — safe); after mirroring, the in-instance entry is a symlink. `sessions` is already a precedent of the same shape.
- Files (`auth.json`, `models-store.json`) must not be pre-created because their content belongs to Pi; instead, create **dangling-tolerant** symlinks inside the instance. Pi checks existence with `existsSync`, so a dangling link reads as "no file", and writes pass through the link to materialize as real files in the real agentDir (verified: Pi writes in place with `writeFileSync`, no rename, and `normalizePath` does no realpath). The seed step runs after broken-link cleanup, otherwise the dangling links would be cleaned away.

The effect is that third parties and Pi write real paths from the very first launch: the ledger's `recordPath`, records' `ownerSessionId`, and artifact paths never contain instance paths.

Rejected design A: absorb on reclaim (move unrecognized entries into the real agentDir). Persisted `recordPath` / `ownerSessionId` / `artifacts[].path` point at the deleted instance path; after a move the ledger treats those pointers as stale and clears them. Fixing that means rewriting third-party file formats plus a conflict-merge strategy.
Rejected design B: point `missions` at the project `.pi/subagents/missions`. The launcher would create files on behalf of unmanaged — even untrusted — projects, breaking the trust gate.
Rejected design C: enumerate more third-party state directories. The list is compatibility debt that silently fails when an extension changes paths; only entries with observed evidence are admitted, and the rest are backstopped by decision 3's warning.
Rejected design D: pre-create `auth.json` / `models-store.json` with Pi's empty values (`{}`). Locks would land on the real paths, but it hardcodes Pi's internal empty-value shape: when Pi later changes format without rewriting the file, a stale file is left behind, whereas the symlink approach lets Pi own the file format forever.

ADR required: per-launch-instance-lifecycle

### 5. No legacy-shape compatibility

The sweep only handles the current generation shape (`launch-` prefix); other directories are neither deleted nor migrated. This way legacy directories from old versions are never misjudged by the upgraded sweep, at the cost of their permanent residue (recorded in the architecture document's known limitations).

## Risks / Trade-offs

- The seed list silently goes stale when third parties change paths → decision 3's warning turns it into a visible, actionable failure; the list table in the architecture document notes "entries require observed evidence, not inference".
- File-class seeds use dangling symlinks: Pi locks `auth.json` / `models-store.json` with `proper-lockfile` at `<instance>/auth.json.lock` (next to the symlink path), so two concurrent instances do not serialize writes to the same real file and could theoretically lose one credential refresh. This is the same class of gap the per-profile copies already had before this change, and no actual impact has been observed; if strong lock consistency is needed, the only way back is "create the files ourselves with Pi's empty values" (rejected design D).
- Dead directories within the grace period linger temporarily → reclaimed at the next launch; disk cost is KB-scale.
- PID reuse can wrongly keep a directory that should be reclaimed → self-healing: it is reclaimed once that pid exits.
- Directories left by failed launches (crash before the pid write) race with concurrent launches → covered by the grace period; another launcher will not delete them by mistake.
- The seed creates empty directories under the real agentDir (`sessions`, `missions`) → consistent with existing behavior: only the directories themselves are created, never their content; file-class paths are not created.
- When a process is force-killed, `proper-lockfile` may leave entries like `<auth.json>.lock` → treated as unrecognized entries: kept and warned about, never silently deleted.
- After upgrade, 0.4.x directories linger permanently, with mission records carrying old absolute paths → covered by the architecture document's known limitations and migration notes.

## Migration Plan

No automatic migration code. After upgrade: new instance directories are generated in the `launch-` shape; old `instances/<profile>/agent` directories stay as-is and can be deleted by the user when needed. The mission records inside can be copied directly into the corresponding project directory of the real agentDir and will continue to be listed and resumable, but the path fields inside the records still point at old paths. To avoid this class of problem long-term, users can point pi-subagents' `missions.directory` at a fixed path so new records no longer depend on agentDir.
